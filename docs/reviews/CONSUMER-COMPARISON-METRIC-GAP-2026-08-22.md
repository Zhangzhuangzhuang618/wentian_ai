# API—消费端重合度公式缺口复核

> 状态：待产品方法决策  
> 发现日期：2026-08-22  
> 影响范围：`API—消费端重合度@K`数值，不影响比较等级和Web端观察指标

## 发现

批准基线已经定义：

- `exact | approximate | query_only`三种比较等级；
- exact和approximate可显示重合度；
- query_only只能并列来源集合，不能返回模型一致性数值；
- 两组样本基数、Top-K集合和模型等价版本必须独立返回。

但基线没有定义`API—消费端重合度@K`的计算公式、分母及跨问题聚合方式。信源“提名—引用重合度@K”另有`|交集| / K`公式，不能在没有明确决策的情况下自动套用到API—消费端指标。

## 为什么不能直接实现

以下算法会产生不同数值和解释：

- 固定K分母：`|A∩B| / K`；
- Jaccard：`|A∩B| / |A∪B|`；
- Overlap coefficient：`|A∩B| / min(|A|, |B|)`；
- 先按问题计算再平均，或先汇总Top-K后计算。

这是指标语义选择，不是代码细节。依据项目变更规则，开发不能自行选择。

## 当前处理

- WT-013只实现有明确公式的Web端可见引用率、首位可见引用率和来源稳定度；
- 现有`deriveConsumerComparisonTier()`继续负责失败关闭到`query_only`；
- 在公式获批前，不生成API—消费端数值重合度，也不以0代替不可用；
- 后续UI可以先显示比较等级和同题并列集合，但不得显示“一致率”。

## 待决策项

1. Top-K重合度的分母；
2. 两侧不足K时的处理；
3. 多样本先聚合还是逐样本配对；
4. 跨问题采用等权问题平均还是按样本加权；
5. 无来源—无来源是否排除并标记无来源；
6. exact与approximate是否共用公式，仅警告不同。

决策后应新增方法ADR或变更记录，并补充黄金数据，不能直接修改批准基线原文。
